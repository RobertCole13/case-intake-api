---
name: remediate-finding
description: Remediate a scanner or assessor finding mapped to a NIST 800-53 control. Reads the control note, finds or proposes the rule, maps blast radius, plans, writes failing tests, fixes, reviews, and assembles the validation package. Invoke with the ticket text, in Plan mode.
disable-model-invocation: true
---
You are remediating exactly one finding. Do not start on another.

1. Parse the ticket: finding id, control ids, CWE, affected locations, severity, evidence required. Restate them in one line and continue. If no ticket or finding text was given, ask for it and stop. The finding id is not a GitHub issue number. Resolve the GitHub ticket from `.harness/findings.yml` (`findings.<id>.github_issue`) and keep that number for step 10. When that key is present, do not call GitHub yet and do not use `issue_read` just to confirm it. If the key is missing, use the GitHub MCP to find one open issue whose title starts with `Finding <id>:` (label `finding` when available). Never treat the finding id as the issue number. Never create a GitHub issue for the finding ticket. If no matching issue exists, stop and say so.
2. Load the control knowledge: read .harness/system.yml (categorization, catalog revision, implemented controls, parameter values, deviations). If a control in the ticket is not listed as implemented, flag it at the top of the plan as a question for the ISSO, and continue. For each control id, read controls/<id>.md (the shared note; managed, never edit it). If it does not exist, read controls/proposed/<id>.md if a draft is already pending. If neither exists, run `npm run control -- <id>` to print the catalog entry and draft the content of controls/proposed/<id>.md in the standard shape, marked PROPOSED, as full text in the plan; nothing is edited before approval. The draft must hold in any codebase: name no path, file, function, table, route, fixture, or domain term specific to this system, and refer to parameter values by their name in system.yml, never by value. Continue using the draft.
3. Find the rules: read .cursor/rules/shared/<id>.mdc (shared; managed, never edit it) and .cursor/rules/local/<id>.mdc (this repo's where and how). If no shared rule exists, draft a generic one for controls/proposed/ in the same shape as the shared rules, marked PROPOSED and holding in any codebase; never place it under .cursor/rules/. If no local rule exists, draft one for .cursor/rules/local/ from the note's code pattern and this repo's layout, unlabeled. Every draft goes into the plan as full text with its target path. Precedence: the shared note and rule say what must be true; the local rule says where, how, and with which values; a local rule may tighten a shared requirement and never loosen it. If the fix seems to need loosening, stop and tell the developer it is a deviation for the ISSO. Never edit a shared rule or note. If .harness/system.yml lists an approved deviation for this control, follow it and cite its ID in the plan.
4. Invoke the `researcher` subagent by name; do not search the codebase yourself before its report arrives. Ask for a short list only: each route the finding touches (method and path), each sibling that returns the same kind of record and whether it is in scope, and which deny tests are missing. Tell it not to quote source and not to propose a fix. Keep that Task prompt short: ticket one-liner, the three list headings, and the bans. Do not paste the full control note or local rule into the researcher prompt. When the report arrives, run one search of the router files yourself (paths under `src/routes/` only) and list any path the researcher missed. Then check deny coverage under `tests/` only: if the researcher says no deny tests are missing but matching deny coverage is not on disk for every in-scope route, treat those routes as missing deny tests. The plan must list concrete negative tests to add (one per in-scope path, plus the audit assertion), never optional "confirm or add" language. Then go straight to step 5. Do not open the services, the seed, the evidence script, the error handler, httpError, the Jest config, package.json, prisma files, or any other file outside `src/routes/` and that `tests/` deny check before the plan. The note and the local rule already name the function and the files.
5. Produce the plan now. Call CreatePlan when available, and also put the full plan body in your visible chat message so the developer can approve even if the Plan UI does not appear. The plan includes: the GitHub issue number from step 1, any drafts from steps 2 and 3 as full text with their target paths, files to change, the fix pattern from the note, the negative tests to add (one per path, asserting status and absence of record fields), the positive tests, the audit-event assertion, the evidence artifacts to produce, and a fenced ```declared-paths block listing every file the change may touch. The plan must not change prisma/schema.prisma, prisma/seed.ts, package.json, or jest config. npm test does not regenerate the Prisma client, so a new column fails the suite before the finding can be shown. A value the schema cannot store goes in an existing column. Every declared path is a concrete repo path. Do not list a placeholder such as <sha>. The evidence image is named when npm run evidence runs and is not listed in advance. End your turn with the single line `Approve the plan? (yes / edits)`. Do not call any tool after that line. Do not say a Plan card is waiting. Do not edit before the developer replies yes (or Build).
6. First write to disk the approved declared paths as .harness/scope/<id>.txt, one path per line, and any drafts in the approved plan, exactly as approved; commit them before any code changes. Then write the negative tests. They exercise routes over HTTP with supertest and import nothing that does not yet exist. Run the suite with exactly `npm test` and no prefix, suffix, or chained command. Confirm the new tests fail on their assertions, not on setup or compilation; report the failing assertion lines.
7. Implement the fix across every path in the plan. Run exactly `npm test` again. Do not report done with a failing test. Do not edit the seed, test fixtures, or test configuration to make tests pass.
8. Review, at most two passes. (a) Only after the suite is green, invoke the `reviewer` subagent with the full diff and the control note (pass 1). Paste its numbered list verbatim. If it reports nothing, go to step 9. (b) If it reports items, STOP and present them to the developer, each with your recommendation: fix now, new finding, or reject. End your turn with the single line `Decide each item: fix / new finding / reject`. Do not edit before the developer decides. (c) For each item marked fix: write a new negative test for that exact attack, run it and confirm it fails on its assertion, implement the fix, then run the full test suite and confirm every test passes, including all earlier tests. If a fix needs a file outside the declared paths, stop and ask for a plan change. (d) Invoke the `reviewer` again (pass 2) with the full diff for context, instructed to attack only the changes made in (c). Paste its list verbatim. (e) Do not run a third pass. Record every item from both passes, the developer's decision on each, and the result, for the PR body; anything pass 2 raised is listed there for the developer at merge.
9. Capture evidence by running exactly `npm run evidence -- <id>` as its own command. Do not chain another command, set or unset variables, or check git status first. If that command fails, stop and report the error. Do not rewrite it. The script writes evidence/<id>/deny.json and evidence/<id>/<id>-<control>-deny-<sha>.png. Read the denial from deny.json. Do not query the database. Draft the retest procedure and a remediation note in assessment language. Do not wait for CI, poll checks, download logs, or kill processes. If a check is still running, say so. If CodeQL failed because default setup is also enabled, report that and stop. Do not edit the workflow.
10. Commit on branch finding/<id>. Include `evidence/<id>/deny.json` in the commit when the evidence command wrote it; the png may be unlisted in the scope file and is allowed by the scope-check pattern. Push with exactly `git push -u origin HEAD` and no other command in that line. Then publish, using the issue number from step 1, in this order: (a) GitHub MCP `add_issue_comment` on that issue with the evidence summary and the five-line Monday card; (b) GitHub MCP `issue_write` to add label `ready-for-ISSO` on that issue (keep any existing labels such as `finding`); (c) GitHub MCP `create_pull_request` titled `<id>: <control> remediation` with body listing changed files against the declared paths, tests and result lines, the rule applied or proposed, the reviewer summary and dispositions, the evidence artifacts, the retest procedure, the remediation note, and `Refs #<github_issue>`. Do not create a new GitHub issue for the finding. Do not comment on or label any other issue. An Allow/Accept tool card is not the same as a completed write. If a GitHub MCP write returns only an "interactive form" / "wait for Submit" message and no comment url, updated labels, or PR url follows, do not claim a form is open on screen — the edit UI often never appears after Accept. For that stalled step only, fall back once to the matching `gh` command (`gh issue edit <n> --add-label ready-for-ISSO` or `gh pr create ...`) so the developer gets a normal shell approval card that actually runs. If that `gh` call is denied or fails, stop and paste the exact command plus the PR title and body for the developer. Never claim an approval card is waiting; either report the tool result (PR url, comment url, labels) or report that the write did not complete and stop. If the GitHub MCP is not configured, stop and say so. Do not use git show, git fetch, sqlite3, or kill. If the plan contained generic drafts, add: after the PR merges, offer to open one issue per control on the plugin repo through the GitHub MCP with both drafts attached. Report what a human must still do: review and approve the PR, deploy through change control, attach the package and request closure, validate, close the POA&M.
