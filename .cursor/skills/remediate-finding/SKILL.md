---
name: remediate-finding
description: Remediate a scanner or assessor finding mapped to a NIST 800-53 control. Reads the control note, finds or proposes the rule, maps blast radius, plans, writes failing tests, fixes, reviews, and assembles the validation package. Invoke with the ticket text, in Plan mode.
disable-model-invocation: true
---
You are remediating exactly one finding. Do not start on another.

1. Parse the ticket: finding id, control ids, CWE, affected locations, severity, evidence required. Restate them in one line and continue. If no ticket or finding text was given, ask for it and stop.
2. Load the control knowledge: read .harness/system.yml (categorization, catalog revision, implemented controls, parameter values, deviations). If a control in the ticket is not listed as implemented, flag it at the top of the plan as a question for the ISSO, and continue. For each control id, read controls/<id>.md (the shared note; managed, never edit it). If it does not exist, read controls/proposed/<id>.md if a draft is already pending. If neither exists, run `npm run control -- <id>` to print the catalog entry and draft the content of controls/proposed/<id>.md in the standard shape, marked PROPOSED, as full text in the plan; nothing is edited before approval. The draft must hold in any codebase: name no path, file, function, table, route, fixture, or domain term specific to this system, and refer to parameter values by their name in system.yml, never by value. Continue using the draft.
3. Find the rules: read .cursor/rules/shared/<id>.mdc (shared; managed, never edit it) and .cursor/rules/local/<id>.mdc (this repo's where and how). If no shared rule exists, draft a generic one for controls/proposed/ in the same shape as the shared rules, marked PROPOSED and holding in any codebase; never place it under .cursor/rules/. If no local rule exists, draft one for .cursor/rules/local/ from the note's code pattern and this repo's layout, unlabeled. Every draft goes into the plan as full text with its target path. Precedence: the shared note and rule say what must be true; the local rule says where, how, and with which values; a local rule may tighten a shared requirement and never loosen it. If the fix seems to need loosening, stop and tell the developer it is a deviation for the ISSO. Never edit a shared rule or note. If .harness/system.yml lists an approved deviation for this control, follow it and cite its ID in the plan.
4. Invoke the `researcher` subagent by name; do not search the codebase yourself before its report arrives. Ask for: every code path the finding touches, every sibling that shares the pattern named in the note, the data flow from request to data layer, existing tests that cover them. When the report arrives, run one search of the router files yourself and list any path the researcher missed.
5. Produce the plan as a Plan (not prose): any drafts from steps 2 and 3 as full text with their target paths, files to change, the fix pattern from the note, the negative tests to add (one per path, asserting status and absence of record fields), the positive tests, the audit-event assertion, the evidence artifacts to produce, and a fenced ```declared-paths block listing every file the change may touch. The plan must not change prisma/schema.prisma, prisma/seed.ts, package.json, or jest config. npm test does not regenerate the Prisma client, so a new column fails the suite before the finding can be shown. A value the schema cannot store goes in an existing column. Every declared path is a concrete repo path. Do not list a placeholder such as <sha>. The evidence image is named when npm run evidence runs and is not listed in advance. End your turn with the single line `Approve the plan? (yes / edits)`. Do not call any tool after writing the plan. Do not edit before approval.
6. First write to disk the approved declared paths as .harness/scope/<id>.txt, one path per line, and any drafts in the approved plan, exactly as approved; commit them before any code changes. Then write the negative tests. They exercise routes over HTTP with supertest and import nothing that does not yet exist. Run the suite with exactly `npm test` and no prefix, suffix, or chained command. Confirm the new tests fail on their assertions, not on setup or compilation; report the failing assertion lines.
7. Implement the fix across every path in the plan. Run exactly `npm test` again. Do not report done with a failing test. Do not edit the seed, test fixtures, or test configuration to make tests pass.
8. Review, at most two passes. (a) Only after the suite is green, invoke the `reviewer` subagent with the full diff and the control note (pass 1). Paste its numbered list verbatim. If it reports nothing, go to step 9. (b) If it reports items, STOP and present them to the developer, each with your recommendation: fix now, new finding, or reject. End your turn with the single line `Decide each item: fix / new finding / reject`. Do not edit before the developer decides. (c) For each item marked fix: write a new negative test for that exact attack, run it and confirm it fails on its assertion, implement the fix, then run the full test suite and confirm every test passes, including all earlier tests. If a fix needs a file outside the declared paths, stop and ask for a plan change. (d) Invoke the `reviewer` again (pass 2) with the full diff for context, instructed to attack only the changes made in (c). Paste its list verbatim. (e) Do not run a third pass. Record every item from both passes, the developer's decision on each, and the result, for the PR body; anything pass 2 raised is listed there for the developer at merge.
9. Capture evidence by running exactly `npm run evidence -- <id>` as its own command. Do not chain another command, set or unset variables, or check git status first. If that command fails, stop and report the error. Do not rewrite it. The script writes evidence/<id>/deny.json and evidence/<id>/<id>-<control>-deny-<sha>.png. Read the denial from deny.json. Do not query the database. Draft the retest procedure and a remediation note in assessment language. Do not wait for CI, poll checks, download logs, or kill processes. If a check is still running, say so. If CodeQL failed because default setup is also enabled, report that and stop. Do not edit the workflow.
10. Commit on branch finding/<id>. Push with exactly `git push -u origin HEAD` and no other command in that line. Open a pull request through the GitHub MCP titled "<id>: <control> remediation" whose body lists: changed files against the declared paths, tests added with their result lines, the rule applied or proposed, the reviewer summary and dispositions, the evidence artifacts, the retest procedure, the remediation note. Post the evidence summary and the five-line Monday card to the ticket and label it ready-for-ISSO. If the GitHub MCP is not configured, stop and say so. Do not use gh, git show, git fetch, sqlite3, or kill. If the plan contained generic drafts, add: after the PR merges, offer to open one issue per control on the plugin repo through the GitHub MCP with both drafts attached. Report what a human must still do: review and approve the PR, deploy through change control, attach the package and request closure, validate, close the POA&M.
